## 1. 目標

在既有 `/guides` 入口與 `/guides/{slug}` 動態路由（`content/guides/*.mdx` + `src/lib/guides.ts` + `src/app/guides/`）之下，完成任務 **18926–18941** 這批新式限時副本的攻略。共 **16 個任務 ID**；因為部分任務可能同副本、不同任務步驟（見 §4 的合篇問題），**實際成篇數待與使用者逐項核可後才能確定**，不預先假設是 16 個任務就等於 16 篇。

明確排除本輪範圍：
- 舊式迷宮／早期副本（雲夢湖底、九秀冰窖等 stage 型迷宮、家族／伺服器控制的日月迷宮、神武玄天塔 8 關、天罡之戰）不在本輪。
- 已議定分類（category）分為兩類：**角色培養**（沿用現有 `GuideStage` 路線站點，即新手起步／轉副門派／進階任務／轉生／通用，維持原本的等級路線用途不變）與**迷宮攻略**（本 roadmap 新增的主題分類，即本文件範圍的 18926–18941）。兩者在資料上分開處理，不混用同一 union；`category` 欄位的實作細節（frontmatter schema、與 `GuideStage` 共存方式等）與呈現方式仍待 §3 第一步出草案，交使用者核可，本文件不預先決定實作細節。

## 2. 來源分級與查核原則

沿用 `docs/plans/guide-content-platform-roadmap.md` §3 的四級來源（database／official／field-test／community），並補充本輪特有的分法：

- **本地 DB**：本機 `tthol.sqlite` 現查得到的欄位（`missions`、`mission_events`、`mission_requirements`、`mission_rewards`、`mission_steps`、`mission_refs`、`npc`、`npc_strings`、`items`、`stages`）。查得到的欄位可標「資料庫」。
- **外部 client 解碼**：原始文件（`genbu-dungeon-guides.md`）裡標註「client 腳本解碼」但**本機 DB 查不到對應欄位**的內容（例如逐關的「清光才能過」機關邏輯細節），明確引用原文件並標明「來源：外部 client 解碼（不等同官方公告），未獨立核對」；原文件本身已標明是推測的部分，才照原樣保留推測語氣。
- **社群**：巴哈攻略串等外部連結，需附作者／URL／日期，明確引用其敘述並標明「未獨立核對」；社群原文若本身是推測、猜測語氣，才保留推測語氣，不得無故加重或減輕原文的確定性。
- **實測**：站長或編輯本人實際遊玩觀察，需附條件與日期。

四者不得混寫成同一語氣；每則內容依其實際查核狀態標「已引用來源」或「未獨立核對」，不得因為來源等級較低就一律改寫成推測——原文本身是明確敘述的，照實引用為明確敘述並標明尚未獨立核對；原文本身是推測的，才保留推測用語。DB 查不到的欄位要明說「資料庫查無」，不得比照原文件假設或補猜。

## 5. 每篇攻略的實作 Gate（嚴格逐篇，禁止批次）

每個任務 ID（或經核可的合篇）依序進行以下步驟：**草稿核可前不得實作，實作經使用者確認前不得推進下一篇**。查核及整理草稿可連續進行，不必每個內部步驟都另行核可。

1. **最新 DB 及來源查核**：對該任務 ID 重新查詢本機 `tthol.sqlite`（`missions`、`mission_events`、`mission_requirements`、`mission_rewards`、`mission_steps`、`mission_refs`、`npc`、`stages`、`items`），並比對原文件（`genbu-dungeon-guides.md`）與（如適用）巴哈等社群來源；列出本地 DB 查得到什麼、查不到什麼、與原文件是否衝突。
2. **草案給使用者**：依 §6 的內容骨架寫成草案（含來源標註、entity link 查核結果、未知事項），交給使用者看過。
3. **明確核可後才實作**：使用者核可草案內容與呈現方式後，才寫入 `.mdx` 檔與必要的分類支援程式碼。
4. **驗證／使用者確認**：實作後跑該篇需要的驗證（見 §7），並請使用者確認內容與呈現符合預期。
5. **確認完成，才開始下一篇**：使用者確認後，該篇才算完成；接著才能開始下一個 ID 的第 1 步。

**分類方案核可（§3 第一步）與本文件的建立，都不等於任何一篇攻略的實作已獲批准。**

## 6. 每篇內容骨架（撰寫時必填／必列的欄位）

- **入口**：NPC 名稱＋地圖／座標（若已知）。
- **等級門檻**：來自 `mission_requirements` 的門檻。
- **組隊要求**：是否強制組隊、人數（若資料/來源有提及；查無則寫「資料庫查無，待補」）。
- **限時**：進場時限、道具時效（來自 `missions.help` 或 `mission_events` timer 事件；查無則寫「資料庫查無，待補」）。
- **道具**：入場道具、關卡內取得道具、獎勵道具，附 `/items/{id}` 連結（查核存在才連結）。
- **逐關條件**：依 `mission_steps.plain_text` 與 `mission_events` 整理；client 腳本解碼或社群內容需分句並標明來源等級，不得與 DB 事實混寫。
- **獎勵**：依 `mission_rewards`（若該任務有列）；查無則寫「資料庫查無，待補」，不得抄原文件的推測數字當結論。
- **注意事項**：社群或實測補充，需標作者／URL／日期或實測條件／日期。
- **來源**：條列本篇引用的所有來源（database／外部 client 解碼（不等同官方公告）／community／field-test），區分清楚，不混寫。

站內 ID 驗證規則：
- 每個 `/monsters/{id}`、`/items/{id}`、`/maps/{id}`（對應 `stages.id`）、`/missions/{id}` 連結，撰寫前都要先查 DB 確認該 ID 存在且對應 route 可正常解析。
- 查無或無法連結的 ID，攻略內文只寫名稱、不放連結，並在該篇的查核紀錄裡記錄原因（例如「DB 查無此 npc id」「stages 無此列」）。

- 內容符合現有攻略頁的視覺與繁中／shadcn／lucide 慣例（不新增 emoji 或 Unicode 圖示；沿用既有 `mdx-components.tsx` 標籤如 `<Item>`／`<MapRef>`／`<Monster>`／`<Mission>` 等）。
- 所有來源 URL（若有）與站內連結（`/items`、`/maps`、`/monsters`、`/missions`）已測試可用；查無或連結失敗需在文中或查核紀錄註明原因。
- 不造成既有攻略（6 篇既有 MDX）回歸：不修改既有內容語意，不破壞既有測試假設（`src/lib/__tests__/guides.test.ts` 目前寫死「6 篇」，新增內容時該測試需同步更新為使用者核可後的新任務內容對應篇數，作為實作階段的一部分）。
- 實作完成後執行（依 `package.json` 實際 script 名稱）：
  - `npm run test`（vitest run）
  - `npm run lint`（eslint）
  - `npm run typecheck`（tsc --noEmit）
  - `npm run build`（next build）
  - 若任一項不符（例如既有已知的 ESLint 相容性問題，見 `docs/plans/guide-content-platform-roadmap.md` 第 246 行的既有紀錄），照實在該篇驗證紀錄註明，不得寫成通過。
- 沿用現有動態路由 `src/app/guides/[slug]/page.tsx` 與 `dynamic = "force-dynamic"`（DB 為 runtime mount）；**不強加 `generateStaticParams`**，除非使用者另外要求。
